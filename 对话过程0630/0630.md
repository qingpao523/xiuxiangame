四、封神榜的轻量存在感
4.1 MVP 中的封神榜不是系统，而是压力源

MVP 阶段，封神榜不做成独立玩法，只作为四种表现存在：

榜文碎光
榜文残影
真灵牵引
榜外之人

4.2 榜文碎光

榜文碎光是封神榜逸散出的微弱金纹。

表现方式：

机缘事件奖励。
破劫文案提示。
地图 UI 背景光效。
功德资源包装。

用途：

提示封神榜已经出现，但玩家还未被正式锁定。

示例文案：

天边金榜一闪而没，一缕碎光落入山中。
你虽不知其名，却本能感到真灵微颤。
4.3 榜文残影

榜文残影是封神榜对大劫边缘修士的轻微感应。

表现方式：

破劫时出现。
第 5 天剧情节点出现。
部分机缘中出现。

用途：

制造封神压力，但不做复杂榜单系统。

示例文案：

破劫之时，你看见一行模糊榜文自天边垂落。
其上无名，却似要将你的真灵照出。
4.4 真灵牵引

真灵牵引代表玩家有被封神榜感应的风险。

MVP 不额外做“真灵牵引值”系统，直接用已有的功德 / 劫气表达。

功德降低牵引。
劫气提高牵引。

也就是说：

功德 = 护住真灵。
劫气 = 借大劫变强，但更容易被榜文感应。

4.5 榜外之人

玩家的核心身份是榜外之人。

MVP 中所有破劫目标都应围绕这个身份：

炼气士 → 真人：第一次看见榜文，但没有被锁定。
真人 → 地仙：封神榜第一次真正感应玩家，玩家用道行、功德、法宝暂时挣脱。

第 7 天地仙突破后，玩家获得临时称号：

榜外散修

称号效果可以很轻：

闭关道行 +3%
破劫成功率 +2%

也可以只做展示，不影响数值。

对《封神修道录》来说，我觉得 Godot 是可以选的，而且方向合理。因为你不是做一个管理后台，而是做一款有氛围、有动效、有神话包装的放置游戏。
关键限制要提前知道：
Godot 4 Web 不建议用 C#
官方文档说明 Godot 4 的 C# 项目目前不能导出到 Web。所以你如果做 Web/H5，建议用 Godot 4 + GDScript。

Web 版后台不会持续运行
浏览器标签页不活跃时，Godot 的 _process() 可能暂停。

来结算，不靠后台持续跑。

存档要注意浏览器限制
Godot Web 的 user:// 存档会落到浏览器侧存储，通常依赖 IndexedDB。隐私模式、清缓存、禁用存储可能导致存档不可用。MVP 可以接受，但正式版最好考虑账号/云存档。

Web 导出包会比普通网页大
Godot 引擎本身会带来 WASM 体积。你的游戏如果只是纯文字按钮，React/Vue 更轻；但如果要做游戏氛围，Godot 的成本是值得的。

移动 H5 能跑，但要保守设计
UI 用 Control 节点和容器布局，避免复杂 3D、重粒子、大贴图。你的项目建议做 2D UI + 少量动效。

六、离线收益实现规则
6.1 结算入口

触发离线结算的时机：

游戏启动后读取存档成功。
玩家从后台回到前台并点击收菜。
玩家主动点击闭关页“领取”。

6.2 有效离线时间
raw_minutes = floor((now_unix - last_offline_claim_time) / 60)
effective_minutes = clamp(raw_minutes, 0, offline_limit_minutes)

如果检测到系统时间倒退：

effective_minutes = 0
弹出提示：时间异常，本次不结算离线收益
6.3 离线上限

炼气士：

4 小时。

真人：

8 小时。

地仙：

12 小时。

新号前 24 小时：

12 小时。

6.4 收益倍率
total_multiplier =
1
+ map_bonus
+ root_bonus
+ treasure_bonus
+ calamity_bonus
+ temporary_event_bonus

MVP 阶段不要用多重乘法，避免数值失控。

6.5 道行结算
daoxing_gain =
effective_minutes
× current_realm.base_daoxing_per_min
× total_multiplier
6.6 法力结算
mana_gain =
effective_minutes
× current_realm.base_mana_per_min
× map_multiplier
× treasure_multiplier
6.7 地图掉落

地图掉落按有效离线分钟折算。

MVP 简化：

drop_roll_count = floor(effective_minutes / 10)

每 10 分钟进行一次掉落判定。

6.8 机缘触发

机缘检查：

event_roll_count = floor(effective_minutes / 30)

每日首次收菜：

必定触发 1 次普通或精良机缘。

如果当前已有 pending_event_id：

先弹出未处理机缘。
不重复抽取新机缘。

6.9 结算顺序

固定顺序：

1. 读取存档
2. 获取当前时间
3. 计算有效离线分钟
4. 读取当前境界
5. 读取当前地图
6. 计算总倍率
7. 结算道行
8. 结算法力
9. 结算地图掉落
10. 判断机缘触发
11. 判断可升重状态
12. 写入资源变化
13. 更新 last_offline_claim_time
14. 保存
15. 弹出闭关结算窗口
16. 若有机缘，继续弹出机缘选择窗口
