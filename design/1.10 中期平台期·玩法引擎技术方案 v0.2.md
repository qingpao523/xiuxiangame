# 1.10 中期平台期·玩法引擎技术方案 v0.2

> design/1.x 首日与前七天核心循环系列。本文是**技术方案（technical solution）**，不是内容门槛。
> 来源：实盘测试报告（实盘测试/测试报告.md）体验观察 **E8**——「11-30 分钟平台期无新解锁、无叙事钩子，情绪曲线走平」。
> 证据：run_3 状态时间线 662s→1680s（约 11→28 分钟）无 new unlock；终局停滞于炼神还虚·7 重 19 分钟。
>
> **用户定调（v0.2 重写依据，原话意图）**：「不对的，设计门槛（硬目标）……这个不是本身游戏缺少玩法！正常常规游戏玩法是怎么做的在技术方案上，是不是需要玩法引擎？」
> → 结论：E8 的本质**不是"内容不够"，而是"架构产不出内容"**。v0.1 把问题当成"缺玩法内容"，列了一堆候选玩法（道途/天象/秘境/洞府/转生）——但这些玩法在当前架构下**每一个都要手写一遍逻辑+弹窗+渲染**，无法量产。真正要补的是一台**玩法引擎（Gameplay/Activity Framework）**，让"加一个玩法"从"改三处代码"变成"配一张表 + 注册一个渲染器"。
>
> **v0.1 处置**：原《1.10 中期平台期·灵活选择玩法设计门槛 v0.1》整体降级为本文 **附录 A（内容需求清单）**——它列举的候选玩法仍然有效，但定位为"引擎建成后可量产的第一批内容"，不再是验收门槛。

## 一、问题重述：这不是内容问题，是架构问题

### 1.1 表象（v0.1 看到的）
11-30 分钟走平，缺新动词、缺主动抉择、缺叙事钩子。

### 1.2 真因（v0.2 诊断）
**当前代码无法低成本地产出一个新玩法。** 任何新玩法（哪怕只是"灵潮三选一"这种纯决策）都必须同时改三处、且全是手写：

| # | 改动点 | 现状 | 代价 |
|---|--------|------|------|
| 1 | **逻辑** | `web/js/game.js` 里写一个 bespoke 动词函数（cultivation / battle / alchemy / divination / breakthrough 各写各的） | 每个玩法一套独立状态与结算 |
| 2 | **分发** | `web/js/ui.js:275-290` 的 `if/else if (popup.kind === ...)` 硬编码 16 种弹窗，每种指向一个手写 `renderXxxPopup` | 加一个玩法 = 加一条 else-if + 一个函数 |
| 3 | **渲染** | 每个 `renderXxxPopup` 手写 DOM | 无法复用、无法数据驱动 |

`web/data/` 下虽有 24 张表，但它们只为**固定动词填内容**（action_table 填修行、encounter_table 填遭遇），**没有一张表能"描述一个新玩法让引擎去跑"**。

**结论**：11-30 分钟加不进玩法，不是因为没想到玩法，而是因为**加任何一个都要付一次"三处手写"的固定成本**。内容越多，债务越重。这就是为什么 v0.1 列了 5 个候选玩法却都没动手——它们的边际成本太高。

### 1.3 唯一的好消息：胚胎已经存在
`battle_v2`（卡牌斗法）是当前**唯一**一个自包含、分层清晰的玩法模块，它**恰好就是目标架构的样板**：

| 层 | 现成实现 | 文件 |
|----|----------|------|
| 纯逻辑引擎 | `BattleEngineV2`（`create(state,cfg)` / `startPlayerRound(state,battle)` / `getSlotCount` / `getSkillData` / `_resolveSlots`，不碰 DOM） | `web/js/battle-engine-v2.js` |
| 编排入口 | `Game.startBattleV2(cfg)` → `BattleEngineV2.create()` → `this.queuePopup({ kind:"battle_v2", battle })` | `web/js/game.js:487-489` |
| 渲染器 | `BattleUIV2.renderBattlePopup(panel, battle, state)` / `renderSlotConfig(...)`，由 `popup.kind` 分发 | `web/js/battle-ui-v2.js:329` / `ui.js:281-282` |
| 数据 | `skill_table.json` 等 | `web/data/` |

**玩法引擎要做的，就是把 battle_v2 这套"逻辑引擎 / 编排 / 注册渲染器 / 数据"的四件套，从孤例泛化成全游戏的底座。**

## 二、调研：常规游戏的玩法是怎么"产"出来的

> 综合 CSDN《小游戏引擎架构》、《Game Programming Patterns》（状态模式 / 组件模式 / 命令模式）、插件化架构通用做法。

### 2.1 关键澄清：我们要的不是"渲染/物理引擎"
本游戏是**文字放置修仙**，没有实时渲染、没有物理碰撞，**不需要 Cocos / Unity / Phaser**。我们要的是一台轻量的 **Gameplay Framework / Activity Engine**——专门解决"如何低成本地定义、调度、结算一个玩法活动"。

### 2.2 成熟游戏承载灵活玩法的四件套
| # | 机制 | 作用 | 对应本游戏缺口 |
|---|------|------|----------------|
| 1 | **数据驱动的玩法定义** | 玩法写在表/脚本里，逻辑与代码分离；策划改表即加玩法 | 24 张表只填内容，无法定义玩法 |
| 2 | **状态机运行时（FSM）** | 通用引擎解释玩法定义，统一管理 `开始 → 进行 → 结算` 生命周期 | 每个动词在 game.js 各写一套生命周期 |
| 3 | **插件注册 + 事件总线** | 模块注册进引擎，靠 pub/sub 解耦，互不硬依赖 | ui.js 用 if/else 硬编码分发，强耦合 |
| 4 | **统一上下文/结算接口** | 玩法读玩家状态、写奖励，走同一套契约 | 每个动词自己读 state、自己 `_applyResourceDelta` |

### 2.3 行业规律（解释"为什么必须能量产"）
- **会话时长锚点**：放置类平均单次会话约 8 分钟。11-30 分钟已是第二/三次会话区间，没有新目标玩家直接关闭。
- **激励响应 U 型曲线**：同质奖励响应递减，对策是**切换激励类型**（数值 → 选择权 → 叙事 → 收集）——切换的前提是"能便宜地加新类型"。
- **阶段转型（《放置时代》范式）**：前期建设 → 中期边打边发育 → 后期 Boss，**每阶段引入一个主导动词**。本游戏 11-30 分钟正卡在"该转型却没转"——而转型需要架构能投放新动词。
- **中期留存五件套**（Realm Grinder / Antimatter Dimensions / Cookie Clicker / Cell to Singularity）：①下一个解锁始终可见 ②分层解锁节奏（每 2-5 分钟一新机制）③里程碑被动奖励 ④主动抉择交错 ⑤转生 prestige 元进度。**五件套全靠"能持续投放新内容"支撑——回到架构问题。**

## 三、目标架构：四层最小玩法引擎

> 设计原则：**增量演进，不推倒重写**。battle_v2 不动，先把它"追认"为标准件，再逐层外推。

```
┌─────────────────────────────────────────────────────────────┐
│ ④ 调度层 Scheduler                                            │
│   复用 game.js tick() / unlock-manager / goal-manager / 天象    │
│   按 境界 / 目标 / 天象 / 随机 触发某个玩法定义                  │
└───────────────┬─────────────────────────────────────────────┘
                │ trigger(minigameId, ctx)
┌───────────────▼─────────────────────────────────────────────┐
│ ② 运行时层 GameplayEngine（FSM 解释器 + 事件总线）             │
│   读 ① 的定义 → 跑 开始→进行→结算 → 经 ③ 找渲染器 → 用 ④ 结算    │
│   统一 Context（读 state）+ Settlement（写奖励）契约            │
└───────┬───────────────────────────────┬─────────────────────┘
        │ 读定义                          │ 分发渲染
┌───────▼───────────────┐   ┌───────────▼─────────────────────┐
│ ① 定义层               │   │ ③ 注册层 Renderer Registry        │
│ minigame_table.json    │   │ register(kind, renderFn)         │
│ {id,触发条件,状态机,    │   │ 取代 ui.js:275-290 的 if/else     │
│  奖励hooks,渲染类型}   │   │ battle_v2 / encounter / event…    │
└────────────────────────┘   └─────────────────────────────────┘
```

### 3.1 ① 定义层：`minigame_table.json`（新数据表）
一行 = 一个玩法。字段草案：
```jsonc
{
  "minigame_id": "spirit_tide_choice",        // 灵潮抉择（附录A方案B）
  "trigger": { "type": "celestial", "event": "lingchao", "realm_min": "rq_07" },
  "fsm": [                                     // 状态机：节点 + 转移
    { "state": "choose", "render": "choice_cards",
      "options": [
        { "id": "absorb", "label": "闭关吸纳", "next": "settle_safe" },
        { "id": "venture", "label": "外出历练", "next": "battle_or_reward" },
        { "id": "craft", "label": "炼丹一搏", "next": "settle_craft" }
      ] },
    { "state": "settle_safe", "reward_hook": "grantDaoxing", "end": true }
  ],
  "renderer": "choice_cards",                  // 指向 ③ 注册的渲染器
  "settlement": { "reward_hook": "grantDaoxing", "log": "灵潮退去，道行入账。" }
}
```
要点：玩法的**触发条件、状态流转、奖励**全在表里；代码只提供通用解释器和可复用的渲染器/奖励 hook。

### 3.2 ② 运行时层：`GameplayEngine`（新模块 `web/js/gameplay-engine.js`）
- `register(minigameDef)` / `trigger(minigameId, ctx)` / `advance(choiceId)`。
- 内部一个通用 FSM 解释器：按定义的 `fsm` 走 `开始 → 进行（可多轮抉择）→ 结算`。
- **统一 Context 接口**（读）：`{ state, realm, resources, rng, helpers }`——玩法只读，不直接改 state。
- **统一 Settlement 接口**（写）：`settle(rewards, { log, popup })`，内部复用现有 `Game._applyResourceDelta` / `Game._log` / `Game.queuePopup`。
- **事件总线**：`on('minigame:start' | 'minigame:settle' | 'realm:up' | 'celestial:change')`，让玩法之间、玩法与主线之间解耦（替代 ui.js 的硬编码耦合）。

### 3.3 ③ 注册层：Renderer Registry（改造 `web/js/ui.js`）
- `RendererRegistry.register(kind, renderFn)`；`ui.js:275-290` 的 16 条 `else if (popup.kind === ...)` 改为 `const fn = RendererRegistry.get(popup.kind); fn(panel, popup, state)`。
- 现有 `renderEventPopup / renderEncounterPopup / renderTreasureChoicePopup / renderRaceChoicePopup ...` 原地改造成"被注册的渲染器"，**行为不变，只是从硬编码分发改为注册分发**。
- battle_v2 追认为第一个标准件：`RendererRegistry.register("battle_v2", BattleUIV2.renderBattlePopup)`。

### 3.4 ④ 调度层：复用现有触发设施（不新建）
- 境界触发：`unlock-manager.js` / `realm-manager.js`（到 rq_07 解锁某玩法）。
- 目标触发：`goal-manager.js`（完成某目标开启某玩法）。
- 天象触发：现有天象/异象系统（灵潮抉择挂这里，顺带闭环 E9）。
- 随机/遭遇触发：`encounter_table` + `game.js tick()`。
- 调度层只做一件事：条件满足时调 `GameplayEngine.trigger(minigameId, ctx)`。

## 四、增量落地路线（四步，每步可独立验收、不破坏现有游戏）

```
Step 1｜追认 battle_v2 为标准件（零风险，先定接口）
  - 把 battle_v2 的「逻辑引擎/编排/渲染器/数据」四件套写成接口规范文档。
  - 产出：GameplayModule 接口约定（create/advance/render/settle 四签名）。

Step 2｜建 GameplayEngine + RendererRegistry，迁移 ui.js 分发
  - 新增 web/js/gameplay-engine.js（FSM + Context + Settlement + 事件总线）。
  - ui.js:275-290 的 if/else → RendererRegistry.get(kind)。
  - 现有 16 种弹窗渲染器原地注册，行为不变（回归 = 实盘跑一遍无回归）。

Step 3｜把 encounter / event / treasure_choice 迁成数据驱动
  - 这三类已是"选项→结算"结构，最易表化；迁入 minigame_table.json。
  - 验证引擎 FSM + 结算契约真实可用。

Step 4｜新玩法 = 纯表 + 注册
  - 附录 A 的方案 B 天象抉择 / 方案 A 道途分支，作为首批"纯表玩法"落地。
  - 此时加一个玩法：写一行 minigame_table + （如需新样式）注册一个渲染器。game.js 零 bespoke 改动。
```

## 附录 A：内容需求清单（原 v0.1 候选玩法，降级为"引擎建成后第一批量产内容"）

> 以下玩法**仍然有效**，但不再是验收门槛。它们的共同点是：在旧架构下每个都要"三处手写"，在引擎建成后应为"一行表 + 注册渲染器"。优先级：A/B/E 低成本（纯决策/复用），C/D 需新动词新系统。

- **方案 A 道途分支抉择**（纯决策层）：rq_07 一次性「立道途」，精/气/神三选，各给被动加成与内容倾向；复用择跟脚 profile 三行（成长/体验/天花板）；不可逆「此念既定」仪式感，唯转世可重定。
- **方案 B 天象抉择**（复用钩子，闭环 E9，**首选首批**）：天象异象从被动加成升级为主动三选（闭关吸纳/外出历练/炼丹一搏）；带倒计时 + 离线错过提示，制造 FOMO。一鱼两吃（E8+E9）。
- **方案 C 秘境历练**（roguelike-lite·新动词，成本中高）：rq_08 解锁，N 步随机空间，每步抉择 + 随机遭遇，可重玩。
- **方案 D 洞府灵脉经营**（轻经营·新动词，成本中）：选灵脉主修（聚灵/养魂/淬体），分配资源产被动加成。
- **方案 E 转生进度可视化**（元进度·复用现有系统，成本低）：把转世做成可见目标（距转世差 X 道痕 / 转世继承 Y），让"等道行"变"为转世攒本钱"。
