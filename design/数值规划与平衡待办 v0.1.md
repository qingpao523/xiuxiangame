# 数值规划与平衡待办清单

> **背景**：当前整个游戏的数值**从未做过统一规划与验证**（已知技术债，全局性问题）。
> 本文件是所有数值的**统一台账**：先记**初版占位值**让系统能跑，待后续「统一数值规划」时逐项验证。
> **原则**：不轻易逐项调死数值；初版只为让机制可运行、可体验，最终以统一规划为准。
>
> **状态标记**：🔴 初版(占位·待验证) ｜ 🟡 待验证(现有但未规划) ｜ 🟢 已定(已验证) ｜ ⚪ 待决策(需设计拍板)

## 一、共鸣系统（新增 · 初版）

### 1.1 共鸣倍率（核心）
模型：①② 之间永远夹着敌方一招（轮流底色）。该招的五行属性调节 ①② 共鸣结果。

**节奏决定（用户拍板 · 已更新）**：初版倍率太激进，收敛。**第一期做「克环 + 增幅」**（用户拍板「克环跟增幅第一期先做五行」）：
相克（被破）+ 相生（增强）都做，基于经典五行；减弱仍暂缓。整体往保守调。

| 情形 | 五行关系 | 初版倍率 | 说明 | 状态 |
|---|---|---|---|---|
| 被破 | 中间系 **克** 我方系（如水克火） | **×1.0** | 共鸣失效，无加成（**第一步只做这个**） | 🔴 |
| 基础 | 其余（同气 / 生 / 泄 / 中性） | **×1.3** | 沿用现状，不被克即正常共鸣 | 🔴 |
| 增强 | 中间系 **生** 我方系（如木生火） | **×1.6** | 相生增幅（**第一期·已做**） | 🔴 |
| ~~减弱~~ | ~~我方系 生 中间系~~ | ~~×1.1 → 暂缓~~ | 初版不做，归入基础 | ⏸ 暂缓 |

### 1.2 三连终极
- **判定方式（初版）**：分段判定——①②、②③ 各查一次共鸣表；两段均 ≥基础（均未被破）才触发终极。　⚪ 待决策（分段 vs 整体）
- **终极倍率**：沿用 `web/data/combo_ultimate.json`。　🟡 待验证

### 1.3 元素生克关系（已拍板 · 两层分离）
- **用户拍板（两层分离）**：
  - **体系层** = 体 / 器 / 魂 / 劫（原「雷」改为「体」；火仍存）。体系是 build 选择，**体系之间无相互克制**。
  - **五行层** = 木 / 火 / 土 / 金 / 水，有相生相克，是**驱动共鸣调节**的那一层。
  - **器**的**二级**才带五行；**体系↔五行不存在固定对应**（不做体系→五行映射）。
- **已落地（架构升级 · 用户拍板「共鸣是多通道、要留口子、克环+增幅可不断丰富」）**：
  新建 `web/js/resonance-system.js` **共鸣系统框架**（取代旧 element-system.js，已删除）：
  - **多通道注册表** `registerChannel`：五行共鸣（第一期已接）/ 套装共鸣（如「哪吒三件套」·占位留口子 `enabled:false`）/ 其他共鸣（待接入）。新增通道不改引擎。
  - **五行通道**：关系图 `_rel` **数据驱动**（克环 木克土→土克水→水克火→火克金→金克木；相生 木生火→火生土→土生金→金生水→水生木），可加节点/加边/加新关系类型不断丰富。被破×1.0 / 增强×1.6 / 基础×1.3。
  - **触发原则**：只有「本身带五行」的招式/夹招才触发五行共鸣（`leftWuxing`/`middleWuxing` 都非空）；不带五行 → 该通道不参与（×1.0）。**不是**给 skill_table 无脑加 wuxing。
  - **统一入口** `evaluate(ctx)` 返回 `{mult, broken, enhanced, results[]}`；各通道倍率**相乘**（初版组合规则）。
  - 引擎 `executeSingleSlot` 已改调 `ResonanceSystem.evaluate`；`web/index.html` 与 `resonance_preview.html` 已切换。
- **⚠ 仍阻塞（数据接线）**：招式 `wuxing` 字段 + 敌方夹招五行 尚未挂 → 五行通道当前惰性（恒走同系基础倍率）。
  待挂【二级五行】数据后共鸣才真正被破/增幅。组合规则（相乘/取极值/优先级）为 ⚪ 待决策，第二期加通道时定稿。
- **器=法宝（用户拍板）**：器**无招式**，器本身（`web/data/treasure_table.json` 33 件法宝）是带**属性**的实体，**五行只是其中一个属性**。体/魂/劫 才是招式体系。故**五行共鸣 + 套装共鸣 都源自法宝属性**。
  - 数据现状：treasure_table **无 `wuxing` 字段、无套装 tag**（grep 命中的 set 实为 card_asset_key 误命中）→ 二者皆需新增。
  - 哪吒三件套已存在于数据：乾坤圈(treasure_010)/混天绫(011)/风火轮(012)，但**无套装归属标记**。
  - ✅ 已拍板：**方案 B**（每格斗法栏绑定一件法宝，法宝.wuxing = 该格共鸣左元 leftWuxing）。管线已通：`_resolveSlots` 挂载 `slot.wuxing`；敌方夹招 `intent.wuxing` → `battle._lastEnemyActWuxing`（middleWuxing）；配招 UI 每格加法宝下拉（`slot-treasure`）。烟测验证：绑火灵珠(fire)+敌夹招水(water)→水克火→broken×1.0 生效。
  - ✅ 已定：御剑术/御器术等 weapon spell_type 是**法术**（御器类法术），**不是器(法宝)** → skill_table 这些招式**保留为可放法术**，无需重归类。器(法宝)= treasure_table，与法术分属两套。

### 5.5 平衡原则
- 四修定位：输出(器)/生存(体)/控制(魂)/机制(劫)，PVE 各有最优场景（Boss 战器/体优，持久战魂优，经营/气运劫优），无全能修。

### v1.1 — P0 拉长回合 / 多敌车轮战 / 体修高血（引擎结构改动 + 数值初版）
- 【敌HP公式】create() 普通/adds 路径：敌HP = `enemy_power × powerMult × ENEMY_HP_MULT`，其中 `powerMult = max(1, round(playerHpMax/200))`（与玩家伤害同源）。作用：防止玩家超级拉高战力后一刀秒敌（幂率补偿）。数学上 powerMult 在回合数公式中会约掉（回合数 ≈ enemy_power×mult / (构筑平均伤害S×终极系数)），故该项不改变回合数、只保证进度稳定。攻击力(power)保持 baseHp 不随 mult 膨胀。
- 【ENEMY_HP_MULT=3】🔴初版。生产真实数据实测回合数极不稳定：map_001(炼气刷怪)=1回合 / map_002(zr_03)=17回合且败 / map_003(dx_01)=3回合且败。根因：map.recommended_power(300→99亿) 与 构筑平均伤害 增长率完全不同步，且敌DPS vs 玩家HP 独立击穿生存。证实用户所言「整个游戏数值未统一规划」——无法靠单一倍率稳定回合数。【待数值规划专项】需按地图分档重定 enemy_power→目标回合数映射，而非全局常数。
- 【多敌车轮战】executeSingleSlot 集火改为 `aliveEnemies()[0]`（入场序首位，原为最低血）；enemyGapAct 改为仅最前存活敌行动（原为全员）。符合用户「一个个轮番上去打，第一个打完第二个血量不恢复」。溅射/连锁仍波及余众。
- 【体修高血】BODY_HP_MULT=1.25 🔴初版。benming=body → playerHpMax×1.25。注意：_powerMult 以 playerHpMax 计，故体修高血同时拉高输出（耦合）——符合用户「血量加加、输出加加两个轮番」的设计哲学；若要体修「血厚但伤低」需解耦 HP/伤害（待决策）。
- 【防御维度】🔴待决策（用户要求深度思考，不一定做）。当前纯DPS对轰、玩家只掉血无防御决策——用户明确这是东方修仙「简单的极致化」设计，拒绝西方生存机制。若加防御需不破坏此哲学（候选：护体灵光/法宝护主等修仙化表达，而非格挡/闪避操作）。

### v1.2 — 真·车轮战（后排候场免疫溅射/连锁/追击）
- 【背景】v1.1 车轮战只改了「行动逻辑」（enemyGapAct 仅最前敌行动 + 集火 aliveEnemies()[0]），但伤害逻辑未改——雷系构筑的溅射(splash)/连锁(chain)/追击(chase) 仍波及后排候场怪，实测 3 怪被同时打空，架空了车轮战。用户拍板「同意真车轮战」= 严格逐个击破、第一个打完第二个顶上、血量不恢复。
- 【核心实现】_dealDamageToEnemy(enemy,dmg,battle) @793 顶部加单点守卫：`const front = battle.enemies.find((e) => e.hp > 0); if (front && enemy !== front) return 0;`（注释：真·车轮战，只有最前存活之敌可被伤害，后排候场者免疫溅射/连锁/追击）。选单点守卫而非逐个改溅射 loop，因它自动覆盖所有伤害路径（主击 / 溅射 915,930,946,957 / 连锁 / 追击 1015 / splash 1076 / kill_bonus 900）。
- 【验证·node 引擎级】3 敌各 pin 6000hp。单 slot0 → 仅 front 妖物甲 -5100，乙/丙 保持 6000（溅射不再清后排）✓。逐 slot 日志：slot0[900,6000,6000] → slot1[0,6000,6000](甲死) → slot2[0,0,6000](乙顶上吃 slot2 死，丙候场) → ultimate[0,0,6000]。死亡顺序 甲→乙→丙 严格逐个 ✓。
- 【终极技 gauntlet-safe 确认】_applyUltimate 各 effect_type 皆不破车轮战：multi_hit(五雷轰顶)/sacrifice_burst 只打 mainEnemy=find(hp>0)=front；paralyze_detonate loop 所有敌但只引爆 statuses.mark，而 mark 仅经守卫过的 _dealDamageToEnemy 施加于 front(@892/897)，backups mark=0 故 0 伤；dot_multiply/lifesteal/invincible_reflect 无直接伤害。实测 thunder 终极(paralyze_detonate) 对未受击的丙(mark=0) 做 0 伤、丙保持 6000 候场 ✓。
- 【supersedes v1.1】v1.1「溅射/连锁仍波及余众」一句作废——真车轮战下后排完全免疫。
- 【小瑕疵】attack 事件未带 target 字段（target=undefined），不影响逻辑，可选修。
