## 1. 石海的标准

本轨只取访谈两点，逐句对应：

**② "不能出戏"是前提条件——一切破坏世界可信度的都是罪。**
石海批评的具体形态是"所有反馈都是数字、装备掉落与使用不符"。翻译成本项目的判据：

1. 反馈的语言必须与世界的语言一致。玩家坐在封神世界的洞府里，系统却用"挑战胜利！""目标达成：goal_name"的结算腔对他说话——这是出戏，与"所有反馈都是数字"同罪。
2. 出戏的对照物是"意境表达"：他认可新技术带来的实时渲染叙事。本项目的对应物不是 3D，而是 6.0 画卷三原则下的**文字意境渲染**——"升重不是战力+3000，是你呼出一口气，这口气比从前长了三息"（6.0 原文）。`atmosphere.js` 三层体系证明纯文字+CSS 也能做到。
3. **"不出戏"有一个品类例外必须显式声明**：放置品类的玩家与游戏签的契约是"我挂时间，你给可预期的收益"。离线收益、破劫成功率、HP/伤害——这些数字是契约本身。**藏掉契约数字是另一种出戏**（欺骗玩家的核心需求）。所以本轨的口号不是"消灭数字"，而是"数字在底层、气韵在表现层"。

**⑫ 结构高于实现。**
现状的结构性缺陷（0.4）：气韵文案散落在 6 个 JS 常量里、分级逻辑写死在 if-else 里。这意味着每一次新增反馈，开发者都要重新做一次"该不该气韵化"的判断，且没有工具提醒。石海的判据翻译过来就是：**先建"反馈如何被说出来"的结构（数据表+渲染器+预算），再谈某一句文案写得好不好**。文案可以慢慢打磨，结构错了则每一次新增都在欠债。

对照 6.0 画卷三原则与石海两点，逐环定位差距：

| 环 | 现状 | 标准 | 差距定性 |

## 3. 改善提案（三档，含依赖与次序）

### 3.0 分类设计：判断准则（三问，不逐条枚举）

任何反馈点，依次问三问：

1. **决策问**：玩家下一步行动是否依赖这个数字？（成功率、敌我对比、成本、挂机效率）
   → 是：**保留数字**。数字是契约与决策信息，气韵只能做它的引言，不能替代它。
2. **事件问**：这是不是一次"世界事件"？（升重、破劫、首次见榜文、机缘、解锁）
   → 是：**气韵为主**。世界事件用世界的语言宣告；若含奖励，数字降为次行小字。
3. **频率问**：它高频重复吗？（吐纳、游历、拾取、普攻结算）
   → 是：**气韵轮换+数字压缩+预算降级**。第 N 次重复时自动缩短乃至静默（留白）。

三问交叉出三档处置：**纯气韵**（事件问命中且无决策依赖）/ **双轨**（事件+数字并存：气韵句在上、数字列表在下）/ **纯数字**（决策问命中：进度条、rate-table、HP、伤害浮字）。B 类 12 处中 B1~B3、B9 走气韵/双轨混合，B4~B8、B10~B11 走双轨，B12 是纯架构问题。A 类 6 处全部保留数字，其中 A3 破劫 rate-table 首行已有 `breakthrough_lore` 气韵引言，是双轨的正确样板。

**L1-4 数据注册**：`data_index.json` tables 数组追加 `"feedback_table.json"`（实读确认该文件是表清单，`data-manager.js` 按表加载）；`node audit_completeness.js` 将文案表纳入完整性审计。

**L1-5 处置 B/C 清单**：按 3.0 三问逐点改调用处——B1 战力降次级、B2 拾取浮字双轨、B9 目标达成标题改读 `chapter_goal_table` 既有气韵字段或 feedback_table、C 类 6 个标题改为 feedback_table 的 `channel:"popup_title"` 条目。**此步不新增任何模态弹窗，只改已有反馈的措辞来源。**

改动文件与次序：`feedback_table.json`（新）→ `data_index.json` → `feedback-renderer.js`（新）→ `atmosphere.js` 改造 → `ui-constants.js`/`constants.js` 迁移删常量 → `game.js`/`ui.js` 调用点（B/C 清单）。
依赖：T0 的文案基准与审查清单。验收口径复用 `design/8.5` T1~T4（浮字不压主按钮、生在世界、分量匹配、克制不叠模态）。

### 3.3 档三 · 系统级（气韵事件系统）

**S2-1 语义事件总线**：逻辑层只发领域事件——`action_finished{actionId, resources}`、`realm_up{from, to}`、`breakthrough_result{btId, win}`、`offline_claim{minutes, resources}`、`battle_end{win, stats}`、`event_offered{eventId}`。事件只带逻辑字段（数字仍在底层，服务端可测，对齐 CLAUDE.md"离线/机缘/斗法是纯逻辑"）；表现层 FeedbackRenderer 订阅事件 → 查 `feedback_table` 的 tier/channel → 渲染。这是把"数据为体、画面为用"从数据表延伸到事件流：**哪个反馈走什么语气，由数据声明，不由分支代码决定**（消解 S2）。

**S2-2 反馈预算调度器（防文字通胀的留白机制）**：
- 同池近 10 次不重复；
- 每日气韵长文（≥2 句）配额（建议 ≤20 条），超额自动降级为一句话或静默；
- 同类事件第 N 次自动缩短（首次见榜文给整段叙事，第 30 次游历结算只剩一句甚至只有数字）。
预算状态存 `state.flags`（不入服务端逻辑，纯表现层），转世重置。

**S2-3 预留钩子**：`feedback_id` 即 21.5 文化翻译的结构钩子（翻译按 id 挂语言包，不改渲染器）；feedback_table 支持服务端按赛季下发新版（对齐守则 7"内容按赛季/版本推进"）。

依赖：L1 全部完成（渲染器与数据表就位）；与 `design/20.0` 网游化、Vue 面板迁移并行不冲突——只在表现层加订阅点，不动 `Game._log`/`toast`/`popupQueue` 既有契约。次序：最后。

### 3.4 总次序

```
T0 文案改写（0 行代码，当日）
  → L1 文案入数据+分级渲染器（约 4~5 个文件，含新增 2 个）
    → S2 事件总线+预算调度（与 20.0 并行，只加订阅点）
```

每一档独立可验收、独立可回滚：T0 只回滚 JSON；L1 的 atmosphere.js API 签名不变，回滚即还原内容来源；S2 是增量订阅，回滚即断订阅。

## 4. 风险与取舍（含 CLAUDE.md 八条守则对照）

### 4.1 守则逐条对照

| 守则 | 结论 | 说明 |
|------|------|------|
| 1 好玩优先于功能堆叠 | ✅ 无新增系统 | 本轨是表现层改造，不加任何数值系统 |
| 2 不是点点点，而是参与封神 | ✅ 增益 | 气韵文案是世界观反馈的载体；T0-4 强制锚点检查 |
| 3 前 30 分钟最高优先级 | ✅ 兼容且增益 | 不改 1.9 v0.3 时间轴与弹窗策略表；首次吐纳弹窗（`game.js:310`）保留；L1-5 明确"不新增任何模态"。风险见 4.2-R3 |
| 4 弹窗克制 | ✅ 更严 | 气韵化只走 C2~C4/C6 非阻断通道；C5 大画卷沿用原有单模态；B9 目标达成从 toast+数字改为气韵标题+日志，反馈总量只减不增 |
| 5 不强制养成路线 | ➖ 不涉及 | 不动主按钮状态机 |
| 6 世界观是玩法的一部分 | ✅ 核心收益项 | 本轨全部工作即此条 |
| 7 手游/网游/长期 | ✅ 增益 | 文案数据化 = 服务端可下发、赛季可换、i18n 可挂 |
| 8 先读文档再动手 | ✅ 已执行 | 实读 CLAUDE.md/6.0/1.9/8.5/9.5 v0.2/21.0 + devlog 相关条目（2206-2227 三层反馈批、2807 弹窗减负批） |

### 4.2 风险清单与取舍

- **R1 文字通胀**（最大风险）：气韵长文同样是阅读负担，6.0 自己警告过"所有反馈都是数字"的反面不是"所有反馈都是散文"。对策：≤25 字/句硬规则 + S2-2 预算调度器 + 频率问降级规则。**取舍：宁可少说一句，不可多说一句——留白优先级高于气韵。**
- **R2 放置收益预期被背叛**：若把离线收益、rate-table、HP 气韵化，等于撕毁放置契约。对策：A 类 6 处列为白名单，任何档次的改造不得触碰其数字本体（只允许加气韵引言）。**取舍：数字永远在，气韵只是数字的门面。**
- **R3 前 30 分钟回归**：T0 改 `action_table.complete_text` 会影响首小时高频文案；历史教训（devlog 2807 行）表明反馈措辞是回归热区。对策：T0/L1 完成后必须重跑 1.9 v0.3 §6.2 六维验收与 9.5 走查（`tests/opening-walkthrough.cjs` 关键字不含 action_table 文案，风险低但须实测）；`test/ui-regression.test.js` 黄金快照先行钉死口径。
- **R4 文案质量不稳**：池子迁入数据后由多人/多批次填写，风格可能漂移。对策：《气韵文案审查清单》+ 双视角验收（受众可读性 + 前端美观度，对齐全局约定）。
- **R5 与 21.1 破劫轨的关系**：破劫大画卷已是本轨 P4 资产，21.1 管"劫是什么"（体制设计），21.2 管"反馈怎么说"（表现层），互补不冲突；但 bt 文案若被 21.1 改写，feedback_table 迁移需在其后执行——**建议次序：21.2 的 T0/L1 先行，S2 等 21.1 文案定稿后收编**。
- **R6 过度工程**：S2 事件总线有做大的诱惑。约束：S2 只做"订阅+查表+预算"三件事，不引入通用事件框架；若 vanilla 阶段性能/复杂度吃紧，S2 可无限期后移，L1 已能交付 80% 价值。
